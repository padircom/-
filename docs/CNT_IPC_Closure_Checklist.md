# وضعیت بستن صورت‌وضعیت — ۲۰۲۶-۱۰-۲۶

این سند وضعیت کد و دروازه‌های بیرونی را جدا می‌کند: تکمیل رابط در مخزن
به‌تنهایی تأیید استقرار سازمانی یا صحت شاخص‌ها/فرمول هر پیمان نیست.

## انجام‌شده در این بازبینی

### DDL تحویلی
- `npm run db:schema` اکنون از `SCHEMA` و `generateDdl` در
  `src/services/persistence.ts` استفاده می‌کند، نه استخراج حدسی نام/نوع ستون.
- `database/schema-mssql.sql`، `database/schema-sqlite.sql` و
  `src/services/pmisFullSchema.ts` همگام‌اند؛ تعداد واقعی **۴۱۲ جدول ثبت‌شده**
  است. اعداد تاریخی ۲۲۴/۲۳۱ تعداد جدول‌های استنباط‌شده از metadata نمایشی
  بودند، نه تعداد کل TableDefهای قانونی (شامل MES/CMMS/IIoT/HRM/EDMS).
- `npm run db:schema:check` اختلاف فایل تحویلی با منبع حقیقت را رد می‌کند.
- نصب خالی SQLite واقعاً اجرا شد؛ وجود تمام جدول‌ها، تمام ستون‌ها و ستون‌های
  هش/PKI با تست `server/cnt.schema.delivery.test.mjs` کنترل می‌شود.
- این فایل‌ها **فقط برای دیتابیس خالی** هستند؛ نوع شناسه‌ها و ستون‌ها نسبت
  به DDL حدسی قدیمی تغییر کرده است. روی دیتابیس قدیمی اجرا/جایگزین نکنید.
  برای ارتقای نصب موجود، بکاپ و dry-run مهاجرت‌ها و بررسی checksum/drift
  لازم است؛ مسیر مدیریت موجود `GET /api/data/migrations` و
  `POST /api/data/migrate` است. داده قدیمی نیازمند ارزیابی/انتقال مستقل است.
- اجرای واقعی SQL Server در این محیط انجام نشده؛ پیش از استقرار سازمانی
  باید DDL و مهاجرت ۰۰۷۹ روی SQL Server آزمایشی اجرا و restore آزموده شود.
- `db:seed` فقط seed نمایشی قدیمی می‌سازد؛ داده نصب تولیدی نیست و دیگر
  DDL قانونی را بازنویسی نمی‌کند.

### مرورگر
- `tests/ui/cnt-ipc-files.spec.ts`: سه تست مرورگری با API شبیه‌سازی‌شده؛
  `tests/ui/cnt-adjustment.spec.ts`: دو تست مرورگری برای d14-p4؛ اجرای ترکیبی
  با `cnt-ipc-routing.spec.ts` هفت تست UI را سبز کرد. ۱۶ تست REST تعدیل/مصالح
  نیز همراه محاسبات خالص گذشتند.
- fixture پیمان انتخاب‌شده اضافه شد؛ تست قبلی بدون پیمان اصلاً پنل را رندر
  نمی‌کرد. نمایش پنل، دانلود XLSX/PDF، پیش‌نمایش سپس commit صریح Excel،
  و عدم دانلود پاسخ خطای JSON بررسی شدند.
- اجرای مجدد: `npx playwright test -c tests/ui/playwright.config.ts cnt-ipc-files.spec.ts`
  پس از اجرای Vite روی ۵۱۷۳ و نصب Chromium. متغیر `CHROMIUM_PATH` برای مرورگر
  محلی پشتیبانی می‌شود. در سندباکس از Chromium بسته npm و کتابخانه‌های همراه
  استفاده شد (`LD_LIBRARY_PATH=/tmp/arena-pdf-libs/lib CHROMIUM_PATH=/tmp/chromium`).
- این تست‌ها جایگزین UAT با backend واقعی نیستند؛ دودتست API واقعی روی
  دامنه RBAC پروژه `c1-p1` جدا اجرا شد.

### چرخش CA
- `CNT_IPC_PKI_CA` اکنون فایل/رشته PEM شامل **چند CA مورد اعتماد سرور** می‌پذیرد.
  در دوره چرخش، CA قدیم و جدید را در یک bundle نگه دارید؛ سپس leaf/key جدید
  را فعال کنید. همه replicaها باید bundle یکسان داشته باشند.
- امضای قدیمی با CA قدیمیِ نگه‌داری‌شده معتبر می‌ماند؛ ترتیب bundle مهم نیست.
  حذف عمدی CA قدیم اعتماد امضاهای صادرشده با آن را قطع می‌کند. هیچ CA از
  رکورد گام یا درخواست detached به‌عنوان لنگر اعتماد پذیرفته نمی‌شود.
- تست: نگه‌داری CA قدیم، ترتیب معکوس، حذف CA و دست‌کاری محتوا.
- bundle فهرست صادرکنندگان مستقیم مورد اعتماد است، نه سازنده زنجیره عمومی
  چندواسطه‌ای. برای CA واسط، سیاست اعتماد سازمان باید صریحاً تأیید شود.
- leaf و CA در زمان ارزیابی اعتبارسنجی می‌شوند. زمان ذخیره‌شده امضا TSA نیست؛
  امضای معتبر رمزنگاری به‌تنهایی حکم اعتبار حقوقی یا وضعیت عدم ابطال نیست.

## وضعیت بدهی‌های قبلی
- **دروازه کیفی سمت سرور:** قبلاً در فاز ۳ پیاده شده بود؛ `cntIpcLineGate`
  در `server/index.js` مقدار کلاینت را کنار می‌گذارد و ریزمتره/IR/NCR را
  می‌خواند. تست‌های REST شامل ادعای دروغین و NCR تازه دوباره اجرا شدند.
- **رابط تعدیل d14-p4:** در بازبینی ۲۰۲۶-۱۰-۲۶ تکمیل شد: کاتالوگ شاخص با
  وضعیت پیش‌نویس/انتشار، محاسبهٔ پیش‌نمایش سمت سرور، ضریب اعمال پیمان، ثبت
  صریح تعدیل، دفتر اقلام مابه‌التفاوت و انتخاب صورت‌وضعیت قفل‌نشده. عملیات
  مصالح اکنون `MaterialDiffAmount`، مبنا، کسورات درصدی و VAT سرآیند را بازمحاسبه می‌کند؛
  تطابق پیمان/صورت‌وضعیت هم سرور کنترل می‌کند. تست REST بازحساب با کسورات و
  تست مرورگری مسیر d14-p4 اضافه شدند. این کار تأیید فرمول‌های ویژهٔ هر پیمان
  یا صحت شاخص ابلاغی توسط حسابرس/سازمان برنامه نیست.
- **p8/pmo:** اجرای هدفمند با `--test-concurrency=1` مبنای پذیرش است؛ ۲۱ تست
  عبور کردند. مشکل رقابت concurrency=4 در این تغییر رفع‌شده اعلام نمی‌شود.

## نیازمند محیط و تأیید سازمان (هنوز باز)

1. اجرای SQL Server آزمایشی و ارتقای بکاپ واقعی، تأیید DBA.
2. UAT با گواهی واقعی سازمان و سیاست CA/واسط/ابطال؛ آزمایش چرخش روی replicaها.
3. HSM در این پیاده‌سازی پشتیبانی/تأیید نشده: signer فعلی کلید PEM می‌خواند،
   پس PKCS#11/سرویس امضای سازمانی نیازمند adapter و تست مستقل است.
4. حسابرس/کارفرما باید دوره، فصل، شاخص مبنا، فرمول و ضریب اعمال را برای هر پیمان نمونه‌برداری و تأیید کند؛ UI ورودی و کنترل فنی را فراهم می‌کند، اما درستی شاخص/فرمول قراردادی را خودش تصدیق نمی‌کند.

TSA/RFC3161، OCSP/CRL و دفتر خارجی هش سخت‌سازی آینده‌اند؛ الزامات حقوقی
سازمان ممکن است آنها را به شرط استقرار تبدیل کند. کلید خصوصی/گذرواژه را
در چت، مخزن یا گزارش تست قرار ندهید.
