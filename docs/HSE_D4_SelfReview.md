## لوپ ۲ — 🔴 باگ بحرانی: ایندکس یکتا روی ستون nullable

گزارهٔ تولیدشده:

```sql
CREATE UNIQUE INDEX [UX_WorkPermit_Qr] ON [dbo].[WorkPermit] ([QrToken]);
```

**چرا این می‌شکند:** در SQL Server ایندکس یکتا روی ستون nullable فقط **یک** NULL می‌پذیرد. `QrToken` تازه به جدولی افزوده شده که ردیف دارد؛ همهٔ ردیف‌های قدیمی `NULL` می‌گیرند. با دو پروانهٔ موجود، مهاجرت با خطای تکراری‌بودن شکست می‌خورد — و چون درایور فعال `json` است، هیچ آزمونی این را نمی‌دید.

**اصلاح در ریشه، نه در محل:** `indexDdl()` حالا برای ایندکس یکتایی که دست‌کم یک ستون nullable دارد، خودکار فیلتر می‌سازد:

```sql
CREATE UNIQUE INDEX [UX_WorkPermit_Qr] ON [dbo].[WorkPermit] ([QrToken])
  WHERE [QrToken] IS NOT NULL;
```

**دو ایندکس دیگر همین باگ نهفته را داشتند** و با همین یک اصلاح درست شدند:

| جدول | ایندکس |
|---|---|
| `EquipmentRental` | `UX_EquipmentRental_Contract` |
| `EngineeringProgressSnapshot` | `UX_EngineeringProgressSnapshot` |
| `WorkPermit` | `UX_WorkPermit_Qr` |

دو آزمون محافظ افزوده شد تا قاعده برنگردد: یکی وجود فیلتر روی ستون nullable را می‌سنجد، دیگری **نبودِ** فیلتر روی ستون اجباری را (تا فیلتر بی‌جا به همه‌جا سرایت نکند).

## لوپ ۳ — `IsSafe` واقعاً غیرقابل جعل است؟

## لوپ ۵ — 🔴 ورودی خصمانه: مقدار منفی «ایمن» گزارش می‌شد

| ورودی | رفتار پیشین | رفتار اصلاح‌شده |
|---|---|---|
| `LelPct: -5` | **ایمن ✅ (غلط)** | اندازه‌نگرفته ⛔ |
| `LelPct: 1e9` | ناایمن ✅ | ناایمن ✅ |
| `LelPct: NaN` | اندازه‌نگرفته ✅ | اندازه‌نگرفته ✅ |
| `LelPct: "0"` (رشته) | ۰ ✅ | ۰ ✅ |

**چرا مهم بود:** گازسنج معیوب یا کالیبره‌نشده مقدار منفی می‌دهد. با خواندن آن به‌عنوان «صفر»، **دستگاه خراب سبزترین نتیجهٔ ممکن را تولید می‌کرد** — دقیقاً برعکس آنچه ایمنی لازم دارد.

**اصلاح دوم، عمیق‌تر:** پس از رفع بالا، قرائت `{-5, 20.9, 0, 0}` هنوز `isSafe: true` می‌داد چون سه پارامتر دیگر سالم بودند. برای پروانه‌ای که گازسنجی اجباری دارد، **«هیچ تخلفی نبود» با «همه‌چیز سنجیده شد» یکی نیست.** `canIssuePermit` حالا قرائت ناقص را هم مانع می‌شمارد:

```
گازسنجی ناقص است: حد انفجار (LEL) اندازه‌گیری نشده
```

سه آزمون محافظ افزوده شد.

## لوپ ۶ — 🟡 دور زدن تعلیق ناشی از گاز

قاعدهٔ «ازسرگیری نیازمند گازسنجی تازهٔ ایمن است» فقط در لایهٔ REST بود. موتور `canResumePermit` برای پروانهٔ معلق `ok: true` می‌داد.

**چرا مهم است:** موتور قرار است تنها منبع حقیقت باشد. هر مصرف‌کنندهٔ دیگری (گزارش‌ساز، یکپارچه‌سازی، UI آفلاین) که موتور را صدا بزند و لایهٔ وب را دور بزند، این قاعده را نمی‌دید.

**اصلاح:** قاعده به موتور منتقل شد؛ `canResumePermit(permit, now, gasTests)` حالا سه حالت را جدا می‌کند — سیاههٔ نبود، قرائت ناایمن، قرائت کهنه. اندپوینت `resume` دیگر منطق تکراری ندارد و از موتور می‌خواند. کار سرد که گازسنجی لازم ندارد، بدون سیاهه هم از سر گرفته می‌شود.

## لوپ ۱۰ — 🟡 پل به ماژول راه‌اندازی وصل نبود

`rfsuSafetyClearance` از D1 در موتور بود و درست کار می‌کرد، ولی **هیچ اندپوینتی صدایش نمی‌زد**. یعنی گزارش آمادگی راه‌اندازی ماژول COM هنوز پروانه‌های واقعی را نمی‌دید — شکاف G-05 روی کاغذ بسته بود، در عمل نه.

**اصلاح:** اندپوینت `GET /api/hse/rfsu-clearance/:systemId` افزوده شد. علاوه بر شمارش، **فهرست پروانه‌های مانع** را هم می‌دهد تا کاربر بداند کدام‌ها را باید ببندد، نه فقط چندتا:

```json
{ "clearance": { "ok": false, "openPermits": 1 },
  "blockingPermits": [{ "permitNo": "PTW-SYS", "typeFa": "کار سرد", "statusFa": "معتبر" }] }
```

دو آزمون REST افزوده شد. نکتهٔ ظریفی که آزمون آشکار کرد: پروانهٔ **پیش‌نویس** «باز» نیست — فقط پروانهٔ صادرشده یا معلق مانع RFSU است.
