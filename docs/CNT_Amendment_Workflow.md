# الحاقیهٔ پیمان — ثبت و تصمیم مستقل

## دامنه

در همان میز کار موجود «اجرا ← مالی ← مدیریت پیمان»، زیر فرم شناسنامه و
برای پیمان انتخاب‌شده، فهرست و فرم الحاقیه قرار دارد. ماژول تازه‌ای ساخته نشد.
مرجع سند و کد تغییر، پیوند نرم‌اند؛ بارگذاری فایل و رابط «تغییر مقادیر و کار جدید»
جزو این تحویل نیستند. هیچ دادهٔ نمایشی وارد محیط کاربر نمی‌شود.

## استفاده

- مدیر پیمان: ثبت پیش‌نویس با کد، موضوع، نوع، تاریخ اثر، تغییر مبلغ/مدت و مرجع سند.
- پیش‌نویس قابل ویرایش، ارسال برای تأیید یا لغو (با دلیل) است.
- پس از ارسال فقط مدیر پروژه یا کارفرمای دارای مجوز `cnt.amendment.approve`
  می‌تواند تصویب یا رد کند. ثبت‌کننده و ارسال‌کننده نمی‌توانند تصمیم‌گیرنده باشند؛
  این قید حتی برای مدیر سامانه برقرار است.
- تصویب، رد و لغو نهایی‌اند؛ سابقه حذف نمی‌شود. تغییر بعدی با الحاقیهٔ جدید انجام می‌شود.
- هنگام تعارض نسخه، تغییر ذخیره نمی‌شود؛ رکورد را از فهرست دوباره برای ویرایش انتخاب کنید.
- مرجع سند الزاماً باید به سند واقعی اشاره کند؛ این فیلد پیوست فایل یا تأیید خودکار اصالت سند نیست.

## لایه‌ها و ماندگاری

- `src/services/contractAmendments.ts`: اعتبارسنجی، وضعیت‌ها، تفکیک وظایف و جمع آثار مصوب.
- `server/contractAmendmentApi.js`: API پروژه‌ای، کنترل نقش/دامنه، نسخه و تراکنش.
- `src/services/contractAmendmentApi.ts`: کلاینت با URL نسبی.
- `src/components/ContractAmendmentsPanel.tsx`: فهرست، فرم و اقدامات گردش تأیید.

مسیر پایه: `/api/cnt-amendments/:projectId/contracts/:contractId`

| فعل و پسوند | کارکرد |
|---|---|
| GET | فهرست و مبلغ/مدت جاری مشتق‌شده |
| POST | ثبت پیش‌نویس |
| PATCH /:id | ویرایش پیش‌نویس با RowVersion |
| POST /:id/transitions | submit / approve / reject / cancel با RowVersion |

`ContractAmendment` از CRUD و import عمومی مسدود است.
تغییر وضعیت، به‌روزرسانی `ContractMaster.CurrentAmount` و ثبت AuditLog در **یک تراکنش**
انجام می‌شوند؛ خطا یا تعارض، همه را برمی‌گرداند. مبلغ اولیه و مدت اولیه بازنویسی نمی‌شوند.
مبلغ جاری = مبلغ اولیه + تغییر مبلغ الحاقیه‌های مصوب.
مدت جاری در نمای الحاقیه‌ها = مدت اولیه + تغییر مدت الحاقیه‌های مصوب؛
این تحویل برنامهٔ زمان‌بندی یا تاریخ‌های آن را خودکار تغییر نمی‌دهد.

سوابق مصوب قبلی دست‌نخورده می‌مانند؛ پیش‌نویس قدیمی بدون سند تا زمان تکمیل و ارسال
وارد چرخهٔ تصمیم نمی‌شود. فهرست بیش از ۲۰۰۰ رکورد با خطا بسته می‌شود، نه جمع ناقص.

## ساخت و SQL

```sh
npm run build:cntamend --silent
npm run build:sql --silent
npm run build:rbac --silent
```

فایل‌های موتور سرور تولیدی‌اند و در Git نگهداری نمی‌شوند. فرمان ساخت الحاقیه به زنجیرهٔ
ساخت آزمون‌ها نیز اضافه شده است. از `npm test` برای آزمون محدود این تحویل استفاده نکنید.

برای SQL Server موجود، پس از پشتیبان‌گیری، اسکریپت افزایشی و idempotent
`db/mssql/V004__contract_amendment_workflow.sql` شش ستون nullable اضافه می‌کند.
پیش‌نیاز آن وجود جدول `dbo.ContractAmendment` از اسکیما عمومی ماندگاری است؛
روی دیتابیس فاقد این جدول، اسکریپت متوقف می‌شود. نصب تازه باید اسکیما به‌روز
`src/services/persistence.ts` را بسازد. هیچ FK فیزیکی بین‌ماژولی اضافه نشده است.
در این محیط SQL Server در دسترس نبود؛ اجرای واقعی مهاجرت و پذیرش SQL باقی است.

## آزمون متمرکز

```sh
node --test server/contractAmendment.unit.test.mjs server/contractAmendment.rest.test.mjs
```

آزمون REST، سرور واقعی را با پوشه‌های موقت JSON/فایل بالا می‌آورد و سپس پاک می‌کند؛
به rundata کاربر دست نمی‌زند. پوشش: نقش، دامنهٔ پروژه، منع ورود عمومی، اعتبارسنجی،
تکرار کد، نسخهٔ کهنه، گردش تأیید، SoD در سطح رکورد، اثر مبلغ و مدت، رد/لغو،
rollback اثر نامعتبر، ذخیرهٔ قابل بازخوانی و تصویب هم‌زمان.

### نتیجهٔ بررسی رگرسیون

۷۷ آزمون متمرکز (الحاقیه، فرم‌های قبلی پیمان و میز کار صورت‌وضعیت) موفق شدند.
آزمون مرورگر با دادهٔ موقت: u-contracts ثبت/ارسال → u-pm تصویب؛ مبلغ ۱۱۰۰ و مدت
۱۱۰ روز از مبنای ۱۰۰۰/۱۰۰؛ u-planner امکان ثبت نداشت. دادهٔ موقت پس از آزمون حذف شد.
بررسی گسترده‌تر `server/rbac.test.mjs` دو خطای قدیمی کاتالوگ داشت: انتظار ۴۴۸
مجوز در حالی که HEAD پیش از این تغییر ۴۶۱ مجوز داشت (اکنون با مجوز الحاقیه ۴۶۲)،
و الزام سه‌بخشی بودن کدها در برابر کدهای قبلی `dispute.view` و `change.view`.
این دو آزمون و کدهای نامرتبط تغییر داده نشدند؛ آزمون جدید نقش/دامنهٔ الحاقیه موفق است.
