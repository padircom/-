سند مرجع گزینهٔ ۷ فهرست هشت‌گانه. هدف: هر داده‌ای که از بیرون وارد سامانه می‌شود یا از آن بیرون می‌رود، از یک دروازهٔ واحد، تست‌پذیر و قابل بازرسی عبور کند.

| قلم | مقدار |
| --- | --- |
| نسخهٔ موتور | `itg-v1` |
| موتور خالص | `src/services/integration.ts` (~۹۹۰ خط، بدون وابستگی بیرونی) |
| باندل سرور | `server/itgLogic.js` (esbuild، `npm run build:itg`، gitignore) |

## ۱. جای این لایه در معماری

```
فایل XER / CSV کاربر
        │
        ▼
  itg-v1  (خالص، بدون I/O)  ── تجزیه ─→ نگاشت ─→ اعتبارسنجی ─→ تفاوت‌گیری
        │                                                          │
        │ ردیف‌های قانونی sql-v1                                   │ گزارش ImportIssue[]
        ▼                                                          ▼
  server/index.js  ── repository.upsert ──→  sql-v1  ──→  JSON driver | SQL Server
```

موتور هیچ‌گاه فایل نمی‌خواند، به شبکه وصل نمی‌شود و به پایگاه داده دست نمی‌زند. ورودی‌اش `string` است و خروجی‌اش ردیف و گزارش. به همین دلیل همان کد بدون تغییر هم در Node (مسیرهای API) و هم در مرورگر (پیش‌نمایش زندهٔ رابط کاربری) اجرا می‌شود.

## ۲. تصمیم‌های معماری (ADR)

### ADR-1 — موتور خالص، سرور نازک
تجزیه و اعتبارسنجی هیچ وابستگی به express، multer یا درایور پایگاه داده ندارد. مسیرهای HTTP فقط پوسته‌اند: فایل را به رشته تبدیل می‌کنند، موتور را صدا می‌زنند و نتیجه را می‌نویسند. نتیجهٔ عملی: ۷۹ تست بدون بالا آوردن سرور و بدون فایل موقت اجرا می‌شوند، و همان منطق در مرورگر برای پیش‌نمایش بدون رفت‌وبرگشت شبکه استفاده می‌شود.

### ADR-2 — خروجی مستقیماً ردیف قانونی `sql-v1` است، نه یک مدل میانی
`extractXer` و `parseImport` دقیقاً ستون‌های جدول هدف را تولید می‌کنند (`Id`, `ProjectId`, `WbsId`, `Code`, …). مدل میانی «Activity واردشده» ساخته نشد چون هر مدل میانی یک نقطهٔ واگرایی جدید است. تست‌ها این قرارداد را قفل می‌کنند: نام هر کلید خروجی باید ستون واقعی جدول باشد و همهٔ ستون‌های اجباری غیرمدیریتی باید مقدار داشته باشند.

میدان‌های نمایشی که ستون پایگاه داده نیستند با پیشوند زیرخط می‌آیند (`_status`, `_constraint`, `_calendarId`) و لایهٔ سرور پیش از نوشتن همهٔ کلیدهای `_`دار را حذف می‌کند.

### ADR-3 — شناسه‌های قطعی، پس ورود دوباره امن است
`Id` از ترکیب پروژه و شناسهٔ داخلی پریماورا ساخته می‌شود: `<projectId>:act:<task_id>`, `<projectId>:wbs:<wbs_id>`, `<projectId>:rel:<task_pred_id>`. بنابراین ورود دوبارهٔ همان فایل ردیف تکراری نمی‌سازد؛ `upsert` روی همان کلید می‌نشیند. اثبات عملی: دو بار `commit=1` پشت سر هم → جدول `Activity` همچنان ۵ ردیف، و پیش‌نمایش سوم `unchanged: 5, added: 0` می‌دهد.

برای ورود قالبی که شناسهٔ خارجی ندارد، کلید طبیعی قالب (`keyFields`) به‌علاوهٔ `ProjectId` نقش کلید یکتا را بازی می‌کند و پاسخ تفکیک `inserted` و `updated` را برمی‌گرداند.

### ADR-4 — تفاوت‌گیری پیش از نوشتن، نه بعد از آن
`diffRows(existing, incoming, keyField, compareFields)` قبل از هر نوشتنی اجرا می‌شود و چهار عدد می‌دهد: افزوده، تغییریافته (با فهرست دقیق ستون‌های تغییرکرده)، حذف‌شده و بدون‌تغییر. برنامه‌ریز پیش از تأیید می‌بیند «۱ فعالیت تغییر کرده: `PhysicalPct` از ۶۰ به ۸۵». حالت پیش‌فرض مسیر `POST /api/integration/xer` **پیش‌نمایش** است؛ نوشتن فقط با `commit=1` صریح انجام می‌شود.

`ACTIVITY_COMPARE_FIELDS` عمداً ستون‌های حسابرسی را شامل نمی‌شود، وگرنه هر ورود همه‌چیز را «تغییریافته» نشان می‌داد.

### ADR-5 — ردیف خطادار دور ریخته نمی‌شود، گزارش می‌شود
هر مشکل یک `ImportIssue` است: `{ code, severity, row?, column?, message }`. کدها پایدارند (`E-ITG-CELL`, `W-ITG-XER-ORPHANREL`, `E-ITG-XER-DUPCODE`, `E-ITG-MISSINGCOL`, …) تا رابط کاربری و لاگ بتوانند رویشان تکیه کنند. سکوت ممنوع است: داده‌ای که بی‌سروصدا حذف شود، فردا به‌صورت مغایرت گزارش برمی‌گردد.

قاعدهٔ مسدودسازی: وجود حتی یک `severity: "error"` جلوی `commit` را می‌گیرد (پاسخ ۴۲۲)، اما `warning` فقط نمایش داده می‌شود.

### ADR-6 — تاریخ شمسی فقط با مبدل تزریق‌شده
موتور خودش `jalaali-js` را `import` نمی‌کند؛ امضای توابع یک `JalaliConverter` اختیاری می‌گیرد. اگر تاریخی شبیه شمسی باشد و مبدلی تزریق نشده باشد، خروجی `null` است نه یک تاریخ میلادی غلط. دلیل: تاریخ اشتباه بدتر از تاریخ نبود است — `1405/06/17` اگر میلادی خوانده شود، ۶۲۱ سال خطا تولید می‌کند. سرور `jalaali.toGregorian` را تزریق می‌کند، تست‌ها هم.

ارقام فارسی و عربی (`۱۴۰۵`, `٤٢`) پیش از هر تبدیلی به لاتین نرمال می‌شوند؛ این قاعده روی عدد، درصد و تاریخ اعمال می‌شود.

### ADR-7 — بحرانی بودن از شناوری استنتاج می‌شود، نه از `driving_path_flag`
پریماورا `driving_path_flag` را فقط پس از اجرای «مسیر بحرانی چندگانه» پر می‌کند و در بسیاری از فایل‌های صادرشده بی‌معناست. معیار ما `TotalFloat <= 0` است که همیشه از داده‌های موجود قابل محاسبه است. شناوری منفی هم بحرانی شمرده می‌شود (فعالیت `MEC-2020` با شناوری ۱۶- ساعت).

### ADR-8 — مدت و تأخیر با تقویم اختصاصی هر فعالیت
XER مدت را بر حسب ساعت می‌دهد. تبدیل به روز با «۸» ثابت غلط است وقتی فعالیت روی تقویم ۱۲ ساعته نشسته. `extractCalendars` نگاشت `clndr_id → day_hr_cnt` را می‌سازد و هر فعالیت با تقویم خودش تبدیل می‌شود؛ همین قاعده برای `lag_hr_cnt` روابط هم اعمال می‌شود. تست این را با دو تقویم هم‌زمان اثبات می‌کند: ۳۶۰ ساعت روی تقویم ۱۲ ساعته = ۳۰ روز، نه ۴۵.

### ADR-9 — نگاشت سرستون چندزبانه و مقاوم
`mapHeaders` هر ستون فایل را با فهرست `aliases` هر میدان مقایسه می‌کند، پس از نرمال‌سازی: حذف فاصله‌های اضافی، یکسان‌سازی خط تیره و زیرخط، بی‌تفاوتی به حروف بزرگ و کوچک. یک ستون «کد فعالیت»، «Activity ID»، `task_code` یا `ACTIVITY   ID` همگی به `Code` می‌نشینند. ستون ناشناخته فقط هشدار است (ورود ادامه می‌یابد)، ستون اجباری غایب خطاست (ورود متوقف می‌شود).

### ADR-10 — تجزیه‌گر CSV مطابق RFC 4180، نه `split(",")`
سلول‌های نقل‌قول‌شده حاوی کاما، نقل‌قول دوتایی فرار (`""`) و خط جدید داخل سلول همگی پشتیبانی می‌شوند؛ BOM خورده می‌شود و ردیف کاملاً خالی حذف. `detectDelimiter` بین `,`، `;` و tab تصمیم می‌گیرد و کاماهای داخل نقل‌قول را نمی‌شمارد — این دقیقاً حالتی است که اکسل فارسی با تنظیمات منطقه‌ای ویندوز تولید می‌کند.

### ADR-11 — OpenAPI تولید می‌شود، نوشته نمی‌شود
`generateOpenApi` مشخصات را از خود `SCHEMA` می‌سازد: هر جدول عمومی پنج عملیات (`GET` فهرست، `POST`، `GET`/`PATCH`/`DELETE` تکی)، هر ستون یک `property` با نوع، `format` و `maxLength`، و ستون‌های غیر nullable در `required`. سه فایل YAML دستی موجود در `docs/openapi/` طی زمان با کد واگرا شده بودند؛ سند تولیدی نمی‌تواند واگرا شود. سرآیند `If-Match` و پاسخ ۴۰۹ (هم‌زمانی خوش‌بینانهٔ `sql-v1`) در همان تولید مستند می‌شوند.

`toYaml` هم دست‌ساز است تا وابستگی جدیدی به پروژه اضافه نشود؛ رشته‌های عددی‌نما مثل `"200"` نقل‌قول می‌شوند تا YAML آن‌ها را عدد نخواند.

### ADR-12 — رابط کاربری بدون سرور هم کار می‌کند
`IntegrationCenter` فایل را با `FileReader` در مرورگر می‌خواند و همان موتور را صدا می‌زند. پس تجزیه، اعتبارسنجی، راهنمای ستون‌ها، دانلود قالب و تولید OpenAPI حتی وقتی API خاموش است کار می‌کنند. فقط دکمهٔ «نوشتن در پایگاه داده» به سرور نیاز دارد و اگر پاسخ JSON نگیرد، پیام صریح می‌دهد به‌جای شکست خاموش (همان الگوی `DataLayerPanel`).

## ۳. تجزیه‌گر XER

فایل XER متن جدول‌بندی‌شده با تب است و ساختار بلوکی دارد:

| نشانه | معنا |
| --- | --- |
| `ERMHDR` | سرآیند: نسخه، تاریخ صادرات، نام کاربر و شرکت |
| `%T <TABLE>` | آغاز جدول |
| `%F c1 c2 …` | نام ستون‌های آن جدول |
| `%R v1 v2 …` | یک ردیف |
| `%E` | پایان فایل |

`parseXer` **همهٔ** جدول‌ها را نگه می‌دارد (نسخهٔ قبلی فقط `TASK` را می‌خواند و روابط، WBS و تقویم را دور می‌ریخت). جدول‌های مصرف‌شده:

| جدول XER | مقصد | نکته |
| --- | --- | --- |
| `CALENDAR` | حافظهٔ تبدیل ساعت→روز | `day_hr_cnt`، تقویم پیش‌فرض |
| `PROJECT` | `projectName`, `dataDate` | `last_recalc_date` |
| `PROJWBS` | `WbsNode` | سطح با پیمایش والدها (سقف عمق ۳۰ برای مصونیت از حلقه) |
| `TASK` | `Activity` | وضعیت، تاریخ‌ها، مدت، شناوری، درصد |
| `TASKPRED` | `ActivityRelation` | نوع رابطه و تأخیر |

نگاشت‌ها: `TK_NotStart → not_started`، `TK_Active → in_progress`، `TK_Complete → completed`؛ `PR_FS/SS/FF/SF → FS/SS/FF/SF` (نوع ناشناخته با هشدار به `FS` تنزل می‌کند). محدودیت‌ها (`CS_MSOA`, `CS_MEOB`, …) در میدان نمایشی `_constraint` نگهداری می‌شوند.

## ۴. کاتالوگ قالب‌ها

شش قالب، ۴۲ ستون تعریف‌شده، همگی به جدول واقعی `sql-v1` بسته‌اند:

| کد | عنوان | جدول هدف | کلید طبیعی |
| --- | --- | --- | --- |
| `TPL-ACT` | فعالیت‌های برنامه | `Activity` | `Code` |
| `TPL-PRG` | پیشرفت دوره‌ای | `ProgressEntry` | `ActivityId` + `PeriodId` |
| `TPL-TMS` | تایم‌شیت نیروی انسانی | `Timesheet` | `MemberId` + `WorkDate` |
| `TPL-NCR` | عدم انطباق | `Ncr` | `Code` |
| `TPL-COR` | مکاتبات | `Correspondence` | `Code` |
| `TPL-CST` | حساب‌های هزینه | `CostAccount` | `Code` |

هر میدان دارای نوع (`text`/`int`/`number`/`date`/`bool`/`enum`)، اجباری بودن، حد بالا و پایین، طول بیشینه و فهرست نام‌های مستعار است. `templateGuide` همین قواعد را به جدول راهنمای قابل نمایش تبدیل می‌کند، پس راهنما هرگز از رفتار واقعی اعتبارسنج عقب نمی‌ماند.

آزمون بستهٔ کامل: برای هر شش قالب، فایل نمونه‌ای که خودمان تولید می‌کنیم باید بدون هیچ خطایی دوباره خوانده شود (`templateCsv → parseImport`) و ستون‌های خروجی باید در جدول هدف وجود داشته باشند.

## ۵. مسیرهای HTTP

| مسیر | کار |
| --- | --- |
| `GET /api/integration/status` | آمار، رجیستری اتصال‌دهنده‌ها، فهرست قالب‌ها |
| `POST /api/integration/xer?projectId=…` | پیش‌نمایش XER: شمارش‌ها، تقویم‌ها، مشکلات، تفاوت با پایگاه داده |
| `POST /api/integration/xer?projectId=…&commit=1` | نوشتن WBS + فعالیت + روابط با `upsert` |
| `GET /api/integration/templates` | فهرست قالب‌ها همراه راهنمای ستون‌ها |
| `GET /api/integration/templates/:code.csv?lang=fa\|en` | دانلود قالب با BOM |
| `POST /api/integration/import/:code` | اعتبارسنجی فایل و پیش‌نمایش ۲۵ ردیف اول |
| `POST /api/integration/import/:code?commit=1&projectId=…` | نوشتن با کلید طبیعی؛ پاسخ `inserted`/`updated` |
| `GET /api/openapi.json` · `GET /api/openapi.yaml` | مشخصات تولیدشده از اسکیما |

ورودی هم از `multipart/form-data` (میدان `file`) و هم از JSON (`{ content, fileName }`) پذیرفته می‌شود؛ دومی همان چیزی است که رابط کاربری استفاده می‌کند. سقف حجم و پسوندهای مجاز (`.xer`, `.csv`, `.txt`, `.xlsx`, `.xls`) در یک multer اختصاصی کنترل می‌شوند تا فیلتر MIME عمومی سامانه فایل‌های `application/octet-stream` را رد نکند.

### اثبات end-to-end (اجراشده)

```
POST /xer?projectId=prj-itg              → counts{activities:5, relations:5, wbs:3, calendars:2, errors:0, warnings:2}
                                           diff{added:5, updated:0, removed:0, unchanged:0}
POST /xer?projectId=prj-itg&commit=1     → written{wbs:3, activities:5, relations:5}
POST /xer?projectId=prj-itg              → diff{added:0, updated:0, unchanged:5}      ← تکرارپذیری
POST /xer  (فایل با درصد ۶۰→۸۵)          → updated:1  changed:["PhysicalPct"] 60→85
POST /import/TPL-ACT (یک ردیف خراب)      → valid:1, invalid:1, E-ITG-CELL row 3 «شروع برنامه‌ای»
POST /import/TPL-ACT?commit=1 (خراب)     → HTTP 422 IMPORT_BLOCKED
POST /import/TPL-ACT?commit=1 (سالم)     → inserted:1 → بار دوم updated:1              ← تکرارپذیری
GET  /openapi.json                       → 54 path، 26 مدل
POST /xer بدون projectId                 → 400 · بدون فایل → 400 · قالب ناشناخته → 404
```

## ۶. رابط کاربری

`IntegrationCenter` در تب ۵ «هوش مصنوعی و یکپارچگی» بالای پنل‌های موجود می‌نشیند. **هیچ آیتم جدیدی به سایدبار اصلی اضافه نشده است.** چهار زیربخش:

1. **اتصال‌دهنده‌ها** — جدول شش اتصال‌دهنده با جهت، قالب، جدول هدف و وضعیت (۳ آماده، ۱ ناقص، ۲ برنامه‌ریزی‌شده). وضعیت واقعی گزارش می‌شود، نه وضعیت آرزویی.
2. **ورود XER** — انتخاب فایل یا چسباندن متن، پیش‌نمایش زندهٔ شمارش‌ها، فهرست مشکلات، جدول فعالیت‌ها با برجسته‌سازی بحرانی‌ها، خروجی CSV و دکمهٔ نوشتن که با وجود خطا غیرفعال است.
3. **قالب‌ها** — انتخاب قالب، جدول راهنمای ستون‌ها، دانلود نسخهٔ فارسی/انگلیسی، بارگذاری فایل تکمیل‌شده و گزارش اعتبارسنجی با پیش‌نمایش ردیف‌ها.
4. **OpenAPI** — نمایش YAML یا JSON با دکمهٔ کپی و دانلود.

## ۷. شکاف‌های باقی‌مانده

| کد | موضوع | وضعیت |
| --- | --- | --- |
| I-01 | XLSX واقعی در مرورگر تجزیه نمی‌شود؛ فعلاً CSV. سمت سرور `xlsx` هست ولی به مسیر قالب وصل نشده | باز |
| I-02 | `.mpp` مایکروسافت پروجکت نیاز به سرویس تبدیل بیرونی (MPXJ) دارد | باز، عمدی |
| I-03 | تقویم‌های XER فقط برای تبدیل ساعت→روز استفاده می‌شوند؛ جدول تقویم و روزهای غیرکاری ذخیره نمی‌شود | باز |
| I-04 | منابع و تخصیص‌ها (`RSRC`, `TASKRSRC`) خوانده نمی‌شوند | باز |
| I-05 | بیس‌لاین از XER استخراج نمی‌شود؛ فقط برنامهٔ جاری | باز |
| I-06 | نوشتن دسته‌ای ردیف‌به‌ردیف است، نه در یک تراکنش؛ برای فایل‌های چندهزار فعالیتی باید تراکنشی شود | باز |
| I-07 | اتصال‌دهندهٔ ERP و ایمیل فقط تعریف شده‌اند، پیاده‌سازی ندارند | باز، آگاهانه |
