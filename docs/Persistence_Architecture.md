# لایهٔ ماندگاری داده SQL — معماری (sql-v1)

نسخه ۱.۰ · ۲۰۲۶-۰۹-۰۸ · وضعیت: پیاده‌سازی‌شده و تست‌شده (۷۹ تست)

## ۱. هدف

دو شکاف قدیمی کنترل پروژه:

| شکاف | شرح | وضعیت |
|---|---|---|
| PEX-G1 | داده در فایل‌های TypeScript بود، نه پایگاه داده | بسته شد |
| PEX-G2 | `POST /api/pex/progress` محاسبه می‌کرد ولی **هیچ‌جا ذخیره نمی‌کرد** | بسته شد |

پیش از این یک اسکریپت SQL دستی در `src/services/pmisSchema.ts` وجود داشت — یک
«نقشه» بود، نه لایهٔ ماندگاری: نه نسخه‌بندی داشت، نه مهاجرت، نه مخزن، نه سازندهٔ پرس‌وجو،
و هیچ کدی واقعاً از آن نمی‌نوشت یا نمی‌خواند.

## ۲. تصمیم‌های معماری

- **ADR-P1 — موتور خالص، اجرا جدا.** `src/services/persistence.ts` هیچ اتصالی نمی‌گیرد و
  هیچ کوئری‌ای اجرا نمی‌کند؛ فقط **رشتهٔ SQL و آرایهٔ پارامتر** می‌سازد. نتیجه: کل لایه
  در Node تست می‌شود بدون آنکه SQL Server لازم باشد، و همان کد در مرورگر هم قابل
  استفاده است (پنل ادمین DDL را محلی تولید می‌کند).
- **ADR-P2 — دو درایور، یک قرارداد.**
  - `MssqlDriver` — تولید؛ کوئری پارامتری را روی `mssql` اجرا می‌کند.
  - `JsonFileDriver` — توسعه/سندباکس؛ همان معنا را روی فایل JSON با **نوشتن اتمی**
    (فایل موقت سپس `rename`) پیاده می‌کند.

  چرا درایور فایلی؟ در این محیط SQL Server در دسترس نیست. بدون آن PEX-G2 «روی کاغذ»
  بسته می‌شد ولی در عمل نه. با آن، ماندگاری **همین حالا واقعی است** و سوییچ به SQL
  فقط تنظیم `SQL_SERVER` است. تنزل آرام است تا نبود پایگاه داده کل API را از کار نیندازد.
- **ADR-P3 — هر دو درایور از یک منطق مشترک استفاده می‌کنند.** اعتبارسنجی ردیف،
  نگاشت نوع و **معنای WHERE** (`matchesWhere` / `applySelect`) همه در سرویس خالص‌اند،
  پس رفتار دو درایور واگرا نمی‌شود.
- **ADR-P4 — مقدار هرگز داخل SQL جاسازی نمی‌شود.** `buildInsert/Update/Select/Delete/Count`
  همیشه `{ sql, params }` برمی‌گردانند؛ `@p0…` برای SQL Server و `?` برای SQLite.
  نام جدول و ستون پارامتری‌شدنی نیست، پس تنها دفاع `assertIdentifier()` است که هر
  شناسهٔ خارج از `^[A-Za-z_][A-Za-z0-9_]{0,62}$` را **استثنا می‌دهد، نه فرار**.
- **ADR-P5 — UPDATE و DELETE بدون WHERE استثنا می‌دهند.** یک خط دفاعی ساده در برابر
  پاک شدن کل جدول به‌خاطر شرط خالی.
- **ADR-P6 — کنترل هم‌زمانی خوش‌بینانه.** هر جدول ستون `RowVersion` دارد.
  اگر `expectedRowVersion` بدهید به WHERE اضافه می‌شود؛ صفر ردیف یعنی
  `CONCURRENCY_CONFLICT` — که از `NOT_FOUND` تفکیک می‌شود.
- **ADR-P7 — پنج ستون حسابرسی مشترک** روی همهٔ جدول‌ها:
  `CreatedAt` · `CreatedBy` · `UpdatedAt` · `UpdatedBy` · `RowVersion`.
  `pickWritable()` این ستون‌ها را از بدنهٔ HTTP حذف می‌کند تا کلاینت نتواند
  `CreatedBy` یا `RowVersion` را جعل کند.
- **ADR-P8 — مهاجرت با چک‌سام.** خطرناک‌ترین حالت این است که اسکریپت مهاجرتی که
  قبلاً اجرا شده بعداً ویرایش شود؛ آن‌وقت کد و پایگاه داده بی‌سروصدا واگرا می‌شوند.
  `detectDrift()` این را می‌گیرد و `POST /api/data/migrate` با کد ۴۰۹ متوقف می‌شود.

## ۴. تولید DDL

`generateDdl(dialect)` اسکریپت کامل را از تعریف قانونی می‌سازد — دستی نوشته نمی‌شود.

| | SQL Server | SQLite |
|---|---|---|
| متن | `NVARCHAR(n)` / `NVARCHAR(MAX)` | `TEXT` |
| بولی | `BIT` | `INTEGER` |
| زمان | `DATETIME2` | `TEXT` |
| اعشار | `DECIMAL(p,s)` | `NUMERIC` |
| ایجاد | `IF OBJECT_ID(...) IS NULL` + `GO` | `CREATE TABLE IF NOT EXISTS` |
| صفحه‌بندی | `OFFSET … FETCH NEXT` | `LIMIT … OFFSET` |

نکتهٔ ظریف: `OFFSET/FETCH` در SQL Server بدون `ORDER BY` نامعتبر است، پس اگر
ترتیبی داده نشود سازنده خودش روی کلید اصلی ترتیب می‌گذارد.

## ۶. اعتبارسنجی ردیف

`validateRow(table, row, mode)` پیش از هر نوشتن اجرا می‌شود:

| کد | بررسی |
|---|---|
| `E-SQL-UNKNOWN-COL` | ستونی که در جدول نیست |
| `E-SQL-NOT-NULL` | ستون اجباری بدون پیش‌فرض در حالت درج |
| `E-SQL-LENGTH` | رشتهٔ بلندتر از طول ستون |
| `E-SQL-TYPE` | ناسازگاری نوع (عدد صحیح، بولی، متن، عدد) |
| `E-SQL-DATE` | تاریخی که `YYYY-MM-DD` نیست |
| `E-SQL-DATETIME` | زمانی که ISO نیست |

در حالت `update` ستون غایب اجباری نیست — فقط آنچه فرستاده شده بررسی می‌شود.

## ۷. نقاط انتهایی REST

| متد و مسیر | کار |
|---|---|
| `GET /api/data/schema` | اسکیما، آمار و درایور فعال |
| `GET /api/data/ddl?dialect=` | اسکریپت DDL به‌صورت متن |
| `GET /api/data/migrations` | اجراشده‌ها + برنامه + کاتالوگ |
| `POST /api/data/migrate` | اجرای معلق‌ها؛ ۴۰۹ در صورت واگرایی |
| `GET /api/data/:table` | فهرست با `?where=Col:op:value&order=Col:desc&limit=&offset=` |
| `GET /api/data/:table/:id` | یک رکورد |
| `POST /api/data/:table` | درج |
| `PATCH /api/data/:table/:id` | به‌روزرسانی؛ سرآیند `If-Match: <RowVersion>` |
| `DELETE /api/data/:table/:id` | حذف |
| `GET /api/pex/progress/entries` | تاریخچهٔ ثبت پیشرفت — **روی ماندگاری واقعی** |

فقط ۲۵ جدول از ۳۱ جدول در `PUBLIC_TABLES` قرار دارند؛ `AppUser`، `UserRole`،
`Delegation`، `AuditLog` و `SchemaMigration` از CRUD عمومی خارج‌اند.

کدهای خطا: `422 ROW_VALIDATION_FAILED` (با فهرست ایرادها) · `409 DUPLICATE_KEY` /
`UNIQUE_VIOLATION` / `CONCURRENCY_CONFLICT` · `400 UNKNOWN_COLUMN` ·
`404 UNKNOWN_TABLE` / `NOT_FOUND` · `503 PERSISTENCE_UNAVAILABLE`.

## ۸. رفع PEX-G2 — پیش و پس

پیش از این نقطهٔ انتهایی نتیجه را محاسبه می‌کرد و برمی‌گرداند و تمام. اکنون:

```
POST /api/pex/progress  →  { "id": "progress-mtt1bvou-79jae", "persisted": true,
                             "driver": "json", "physicalPct": 0, "acceptedIntoEv": true }
GET  /api/pex/progress/entries?activityId=ENG-BD  →  { "total": 1, ... }
```

رکورد در `ProgressEntry` می‌نشیند، JSON مربوط به `Steps` رفت‌وبرگشتی سالم می‌ماند،
و پس از راه‌اندازی مجدد سرویس هم موجود است. گیت‌های قبلی (قفل دوره و بازرسی) دست‌نخورده‌اند.

## ۹. رابط کاربری

`src/components/DataLayerPanel.tsx` روی تب سوم «مدیریت سامانه» («۳. لایه داده و
اسکیمای SQL») بالای `SqlConnectionPanel` موجود سوار شد — **بدون افزودن آیتم به
سایدبار اصلی**. چهار زیرتب:

1. **نمای کلی** — درایور فعال (با کاوش زندهٔ API)، آمار، توزیع جدول بر حسب ماژول.
2. **مرورگر اسکیما** — جستجو و فیلتر ماژول، جزئیات ستون‌ها با نوع بر حسب گویش،
   ایندکس‌ها و کلیدهای خارجی.
3. **تولید DDL** — سوییچ SQL Server / SQLite، پیش‌نمای کامل، کپی و دانلود `.sql`.
4. **مهاجرت‌ها** — کاتالوگ با چک‌سام، وضعیت اجراشده، هشدار واگرایی.

پنل بدون API هم کار می‌کند: اسکیما، DDL و برنامهٔ مهاجرت **محلی** محاسبه می‌شوند،
چون سرویس خالص در مرورگر هم اجرا می‌شود. فقط «کدام مهاجرت اجرا شده» از API می‌آید.
