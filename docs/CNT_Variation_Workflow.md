# تغییر مقادیر و کار جدید — d14 / اجرا / مالی / مدیریت پیمان

## رابط و دامنه

گزینهٔ موجود «تغییر مقادیر و کار جدید» در سایدبار اکنون بخش واقعی همین نام
را در همان میز کار و برای همان پیمان انتخاب‌شده باز می‌کند؛ ماژول جدیدی ساخته نشده است.
بخش دو حالت دارد:

- **تغییر مقدار ردیف**: انتخاب ردیف اجرایی فعال فهرست‌بهایی با نرخ توافقی،
  شماره تغییر، مقدار جدید، علت، مرجع سند و کد تغییر مرتبط اختیاری.
- **کار جدید و توافق نرخ**: کد/شماره ردیف تازه، شرح، واحد، مقدار، نرخ پیشنهادی،
  روش تحلیل نرخ، علت و مرجع سند. در تصویب، نرخ توافق‌شده باید صریحاً وارد شود.

پیش‌نویس قابل ویرایش یا لغو با دلیل است؛ پس از ارسال، فقط تصمیم مستقل
مدیر پروژه/کارفرمای مجاز ممکن است. ثبت‌کننده و ارسال‌کننده نمی‌توانند تصمیم‌گیرنده باشند.
تصمیم نهایی و تکرار اثر قفل‌اند. سند، **مرجع نرم به سند واقعی** است، نه بارگذاری فایل
یا راستی‌آزمایی خودکار اصالت آن. این تحویل تحلیل خودکار نرخ یا تعیین نرخ جایگزین ندارد.

## اثر و کنترل‌ها

- تغییر مقدار: مقدار مبنا، نرخ و RowVersion ردیف در سرور ثبت می‌شوند؛ مقدار جدید
  و اختلاف مبلغ محاسبه می‌شود. نرخ این مسیر تغییر نمی‌کند.
- هنگام ارسال و تصویب، مبنا باید هنوز همان نسخه باشد. پیش‌نویس کهنه با ویرایش
  بازبینی می‌شود؛ درخواست ارسال‌شدهٔ کهنه باید رد و با درخواست تازه جایگزین شود.
- مقدار منفی، مقدار یکسان، ردیف مقطوع/تجمیعی/غیرفعال/دارای نرخ نامشخص رد می‌شوند.
- کاهش زیر مجموع متره‌های verified یا کارکرد verified/approved صورت‌وضعیت رد می‌شود.
  این کنترل محافظه‌کارانه است و به معنای برگشت کارکرد گذشته نیست.
- تصویب کار جدید، دقیقاً یک ردیف `unit_price` با `IsStarred=true` و `RateStatus=agreed`
  می‌سازد و شناسه‌اش را در `ExtraWorkItem.BoqItemId` نگه می‌دارد.
- وضعیت درخواست، اثر روی BOQ و AuditLog در **یک تراکنش** ذخیره می‌شوند؛ نسخهٔ
  کهنه، تکرار شماره ردیف یا خطا باعث rollback می‌شود. CAS روی ردیف BOQ هم برقرار است.
- مبلغ اولیه و `ContractMaster.CurrentAmount` تغییر نمی‌کنند؛ افزایش مبلغ پیمان
  فقط در گردش الحاقیهٔ مصوب انجام می‌شود تا دوباره‌شماری نشود. اختلاف BOQ و مبلغ
  پیمان با هشدار موجود نمایش داده می‌شود. صورت‌وضعیت‌های گذشته بازنویسی نمی‌شوند.
- ردیفی که از گردش مصوب آمده است از فرم قدیمی قابل بازنویسی مالی نیست؛ تکمیل
  شرح و نگاشت WBS/CBS با حفظ مقادیر مالی امکان دارد. ثبت اولیهٔ BOQ قبلی حفظ شده است.
- درخواست‌ها از CRUD و import عمومی بسته‌اند؛ هیچ FK بین‌ماژولی اضافه نشده است.
- سوابق قدیمی حذف یا بازنویسی خودکار نمی‌شوند. پیش‌نویس قدیمیِ فاقد سند/نسخهٔ مبنا
  باید پیش از ارسال ویرایش و تکمیل شود. سوابق فاقد هویت تهیه‌کننده/ارسال‌کننده
  برای تصمیم‌گیری fail-closed هستند و نیاز به رسیدگی به سابقه دارند.

## لایه‌ها و API

- منطق خالص: `src/services/contractVariations.ts`
- سرور: `server/contractVariationApi.js`
- کلاینت: `src/services/contractVariationApi.ts`
- رابط: `src/components/ContractVariationsPanel.tsx`

پایه: `/api/cnt-variations/:projectId/contracts/:contractId`

| مسیر | کارکرد |
|---|---|
| GET پایه | فهرست دو نوع درخواست و BOQ همان پیمان |
| POST /quantity یا /extra | ثبت پیش‌نویس |
| PATCH /:kind/:id | ویرایش پیش‌نویس با RowVersion |
| POST /:kind/:id/transitions | submit / approve / reject / cancel |

مشاهده با `cnt.contract.view`، تهیه با `cnt.boq.edit` و تصمیم نهایی با
`cnt.variation.approve` است. دامنهٔ پروژه و تعلق ردیف به پیمان در سرور بررسی می‌شوند.
فهرست‌ها بیش از سقف ۲۰۰۰ درخواست/۲۰۰۰۰ ردیف با خطا بسته می‌شوند تا داده ناقص مبنای تصمیم نشود.

## ساخت و پذیرش

```sh
npm run build:cntvariation --silent
npm run build:sql --silent
npm run build:rbac --silent
npx tsc --noEmit
node --test server/contractVariation.unit.test.mjs server/contractVariation.rest.test.mjs
```

موتور تولیدشده در Git نگهداری نمی‌شود؛ فرمان ساخت به زنجیرهٔ آزمون موجود نیز افزوده شد.
برای پایگاه SQL Server موجود، پس از پشتیبان‌گیری از اسکریپت افزایشی و idempotent
`db/mssql/V005__contract_variation_workflow.sql` استفاده شود؛ پیش‌نیاز آن وجود
جدول‌های عمومی پیمان است. روی نصب تازه، اسکیما به‌روز persistence.ts مبناست.
SQL Server در این محیط در دسترس نبود؛ اجرای واقعی مهاجرت/تراکنش SQL و پذیرش تولید باقی است.
آزمون‌های REST و مرورگر با دادهٔ موقت JSON و حذف آن پس از پایان اجرا می‌شوند، نه rundata کاربر.

### نتیجهٔ این تحویل

۱۰۰ آزمون متمرکز (تغییرات، الحاقیه، فرم‌های قبلی پیمان و میز کار صورت‌وضعیت) موفق شدند.
TypeScript و diff check موفق بودند. آزمون مرورگر مستقل با نقش‌های u-contracts،
u-pm و u-planner مسیر سایدبار، ثبت/ارسال هر دو درخواست، تصویب مقدار و توافق نرخ،
عدم افزایش دوبارهٔ مبلغ پیمان و محدودیت نقش را تأیید کرد. تست مرورگر الحاقیه و
اتصال‌های قبلی سایدبار نیز مجدداً موفق بود. همهٔ داده‌های این تست‌ها موقت و جداگانه بودند.
دو ناسازگاری قدیمی کاتالوگ در آزمون گستردهٔ RBAC (تعداد ثابت مجوزها و کدهای دوبخشی)
که در تحویل الحاقیه مستند شده‌اند، در این مرحله تغییر داده نشدند؛ نقش/دامنهٔ مجوز
جدید تغییرات در آزمون مستقل پوشش داده شد.
